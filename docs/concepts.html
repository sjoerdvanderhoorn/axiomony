Architecture & security

The database is the shared contract. Axiomony exposes a way to define it and work within it—without maintaining a second set of business rules in application middleware.

The database is the contract

Business software needs a consistent representation of customers, suppliers, invoices, orders, approvals and the relationships among them. It also needs clear rules for who may see or change each record, and when. Axiomony makes those contracts the central concern, instead of treating them as an implementation detail of a predefined application.

The current database engine is PostgreSQL. Its actual tables, relationships, column privileges, row-level security policies, constraints, triggers and stored functions are the source of truth. The MCP server inspects and operates on these database objects rather than duplicating them into an independent application rules model.

Administration MCP

An administrator can describe schema changes, authorization rules or workflows in natural language. The server invokes an internal AI planner that examines the live catalog and prepares a proposed SQL migration. The proposal includes a plan ID for review. Nothing is applied until an authorized administrator explicitly approves it with implement_plan.

The SQL executes with the database privileges of the authenticated administrator. Tool visibility does not elevate a user beyond their real database permissions. Proposed plans currently reside in process memory and expire.

Data MCP

Data tools use fixed, parameterized operations to discover accessible tables, inspect columns, and select, insert, update or delete records. Each request authenticates with the individual user's own database credentials. PostgreSQL independently checks applicable privileges and policies at execution time.

Authorization belongs at the source

Imagine ACME's accounting database has a rule requiring approval for invoices of EUR 500 or more. That condition must apply whether the invoice is submitted from Purchasing's mobile form, Finance's dashboard or another client. A generated interface cannot override or bypass a database constraint simply by ignoring it.

The same principle applies to read permissions. The database may allow a salesperson to see their team's orders while keeping restricted payroll and financial records unavailable. The database—not a menu hidden in the interface—decides which results are accessible.

There is an important distinction between permission enforcement and security of credentials: a compromised account may still perform whatever actions that account is allowed to perform. Secure authentication and secret handling remain necessary.

Personal applications and hosting

Once the shared schema and rules are defined, different people can build different interfaces for the same data: an invoice capture tool, a sales pipeline view, a reconciliation workflow or a reporting interface.

The Standalone deployment includes Nginx for publishing user-owned static HTML, CSS and JavaScript. These published files are publicly readable at their URLs. The publishing tools restrict which user may create or edit files, but this is not an authenticated data application runtime.

A standalone browser cannot safely embed reusable PostgreSQL passwords or expose API secrets. Dynamic browser apps require a trusted, authenticated runtime or secure server-side session that accesses Data MCP on behalf of the user. That browser-to-MCP bridge is not included in the current implementation.

No duplicated business-rule middleware

Axiomony's goal is to avoid placing business authorization logic, validation rules and workflow constraints in yet another middleware system that can diverge from the database. The MCP server still provides a necessary protocol interface, and secure clients or runtimes still transport authenticated requests. Neither needs to maintain a second authoritative set of rules for the organization's data.

This distinction makes independently created tools easier to reason about: applications can differ completely in UX while the underlying source of truth and its enforcement remain the same.

Security considerations

!

Do not expose the current MCP endpoint directly to the public internet. It currently authenticates via HTTP Basic carrying reusable database credentials. Add appropriate HTTPS, identity federation/session handling, rate limits and audits before introducing remote users or sensitive business data.

AreaCurrent behavior / important boundary
AuthenticationEach MCP request is verified against PostgreSQL using the presented database username and password; OAuth/OIDC sessions are not included.
AuthorizationDatabase GRANTs, row-level security, column privileges, constraints and triggers enforce access. Permission explanations cannot predict arbitrary SQL function behavior.
AI-generated SQLProposals are inspected and require human approval. The SQL safety checks do not replace isolated testing, independent review or durable audit logs.
Browser applicationsStatic hosting is not an authenticated data runtime. Never store passwords or tokens in browser JavaScript.
IntegrationsExternal services such as banks require their own approved APIs and credentials, handled in a trusted environment.
TestingNode.js and Compose checks run in CI. End-to-end database and hosted-client verification is still needed.

Current scope and direction

The repository contains database catalog inspection, permission-aware data operations, the administration planning and approval flow, optional static site publishing, and REST compatibility. The priority areas are secure identity integration, a trusted browser-to-MCP runtime, stronger SQL migration validation, auditable migrations and end-to-end tests.

See the roadmap, MCP tools and installation options for details.
